# 篇1：魅蓝 Note5 TWRP 服务器项目 —— 背景、路线选择与设备事实

> 时间跨度：2026-10-18 ~ 2026-11-02
> 设备：魅蓝 Note5 (M5 Note, MT6755, aarch64, Android 7.0, kernel 3.18.35)
> 最终目标：**进 recovery 分区即自动成为 Debian chroot 服务器**（不跑安卓框架，省电省内存）
> 本篇聚焦：为什么要做、走过的所有路线、为什么最终选 hybrid recovery + 钩子

---

## 一、项目起源与动机

### 1.1 用户需求演进

1. **最初**：手机当 Debian chroot 服务器用（跑 cpa/cli-proxy-api、freellmapi、sshd、AdGuardHome、mihomo、easytier 等服务）
2. **痛点**：正常开机跑安卓框架（zygote/system_server/ART）+ chroot 服务，内存吃满（~2.5GB 中用 2GB），而且安卓框架本身耗电
3. **用户要求**：**"既要又要"** —— 跑全部 MTK 底层驱动/守护（电量/温控/wifi），但砍掉谷歌框架吃内存的部分
4. **插电常跑**：插电当服务器用，但要防电池鼓包 → 需要读电池容量/温度（fuelgauged）
5. **最终诉求**：**进 recovery 分区即自动成为服务器**，不碰 boot 分区（boot 是手机正常开机的命脉）

### 1.2 为什么选 recovery 分区

- recovery 分区 `mmcblk0p1`（32MB），boot 分区 `mmcblk0p22`（16MB）
- **刷 recovery 不影响正常开机**：刷坏了，手机照样进安卓；再刷回 TWRP 即可
- recovery 分区可逆、风险低

## 三、走过的所有路线（含弯路）

### 3.1 路线 A：Magisk 模块方案（system 版，已工作）

**早期方案**：安卓开机后，Magisk 模块挂载 chroot、配网络、拉 supervisord，Debian 服务在 `/data/debian` 里跑。

**Magisk 模块清单**（7 个，在 `/data/adb/modules/`）：
- `chroot-mount`：挂 proc/sys/dev/devpts + tmpfs
- `chroot-network`：配 DNS/resolv.conf
- `chroot-services`：起 supervisord
- `chroot-netfix`：网络修复
- `static-ip`：静态 IP 192.168.31.213/24
- `adb-tcp`：无线 adb 5555
- `postboot-tune`：开机后调优

**局限**：依赖安卓框架（`getprop sys.boot_completed`、`net.dns1`、安卓管 WiFi）→ 内存吃满、耗电。

### 3.2 路线 B：TWRP 持久化（twrp_slim.img，早期尝试）

**思路**：把逻辑烧进 TWRP 镜像本身（`init.recovery.mt6755.rc` + `sbin/slim_server.sh` 打进 ramdisk），刷多少次 TWRP 都是同一套系统。

**产物**：`twrp_slim.img`（18753615 B，md5 `f2b748b71497d3ff9d948aae09cd3521`）

**问题**：`init.recovery.mt6755.rc` 依赖 TWRP 内 `ro.hardware` 实际值是否为 `mt6755`（未验证）；所有逻辑写死在镜像里，改配置要重刷。

### 3.3 路线 C：改 boot 精简镜像（boot_slim.img，方向错误）

**思路**：改 boot 的 init.rc，砍掉 `class_start main`/`class_start late_start` 和 zygote import，只保留驱动链 + MTK 守护。

**弯路**：
1. **反汇编 `multi_init`**：boot 的 `/init` 是 32 位 ARM 静态 ELF 壳，execv 到 `/sbin/multi_init`（64 位 aarch64 静态，1250664 B），按 `ro.bootmode` 分三支。**浪费大量时间在 capstone 反汇编上，结论：走 TWRP 路线根本不经过 multi_init，无意义。**
2. **纠结 SELinux context**：用户已确认 SELinux 已关闭，seclabel/restorecon 是纯浪费。
3. **改 boot 分区风险高**：boot 是手机正常开机的命脉，改坏了手机变砖。

**结论**：**不要改 boot 分区、不要做 boot 精简镜像**。

### 3.4 路线 D：Magisk 修补 TWRP（twrp-magisk.img，走不通）

**思路**：用 Magisk 的 `boot_patch.sh` + `magiskboot` 修补 TWRP，让 Magisk 在 recovery 里跑模块。

**产物**：`twrp/releases/twrp-magisk.img`（19087360 B），ramdisk 已注入 magiskinit（`skip_initramfs`→`want_initramfs` 已打）。

**致命问题**：**Magisk 检测 `/sbin/recovery` 就 `RecoveryInit` abort（还原 init），不在 TWRP 里跑模块**。Magisk 在 recovery 里会主动 abort。

**结论**：**Magisk 不能用于 recovery**，纯 init.rc 钩子。

### 3.5 路线 E：hybrid recovery + 钩子（最终方案，成功）

**hybrid 内核**：normal 内核（驱动全）+ TWRP ramdisk（调度好）= "既要又要"正解。

**钩子机制**（Magisk 式）：开机自动执行 `/data/local/tmp/twrp-hooks/*.sh`，放脚本即跑，不改镜像。

**最终产物**：`hybrid-hooked.img`（18776064 B），已刷入 recovery 分区 p1。

**详细方案见篇3（hybrid 全自动钩子实战）**。

## 四、路线选择的关键决策点

### 4.1 为什么最终选 hybrid recovery + 钩子

| 路线 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A: Magisk 模块（system） | 已工作 | 依赖安卓框架，内存吃满 | ❌ 不满足"省电" |
| B: twrp_slim.img | 逻辑烧进镜像 | 改配置要重刷，`init.recovery.mt6755.rc` 未验证 | ⚠️ 不灵活 |
| C: boot_slim.img | 精简安卓框架 | 改 boot 风险高，可能变砖 | ❌ 太危险 |
| D: twrp-magisk.img | Magisk 模块化 | **Magisk 在 recovery 会 abort** | ❌ 走不通 |
| **E: hybrid + 钩子** | normal 内核驱动全 + TWRP 调度 + 钩子灵活 | 需要理解 hybrid 合成 | ✅ **最终方案** |

### 4.2 关键技术洞察

1. **内核驱动全 built-in**：原厂内核已含所有驱动，recovery 引导即生效，**不需要安卓框架**
2. **TWRP 调度好**：TWRP ramdisk 不跑安卓框架（zygote/system_server），大核自动睡死（cpu4-7 offline），省电
3. **钩子机制灵活**：`/data/local/tmp/twrp-hooks/*.sh` 放脚本即跑，**不改镜像、不重刷**
4. **hybrid 合成**：normal 内核 + TWRP ramdisk = 驱动全 + 调度好

### 4.3 用户"既要又要"的正解

- **"既要"**：跑全部 MTK 底层驱动/守护（电量/温控/wifi）→ **normal 内核驱动全**
- **"又要"**：砍掉谷歌框架吃内存的部分 → **TWRP ramdisk 不跑框架**
- **hybrid = normal 内核 + TWRP ramdisk** → 驱动全 + 调度好

## 五、核心技术洞察（背景故事）

### 5.1 用户反感"我写的调度脚本"

用户明确说："**你反感我写的调度脚本，要官方二进制/标准化方法（Magisk 模块式钩子）**"。

**所以最终方案**：
- **不用手写热插拔脚本**（`echo 0 > cpuX/online` 这种"我写的"）
- **用官方二进制**：fuelgauged、wpa_supplicant、supervisord
- **用 Magisk 式钩子**：`/data/local/tmp/twrp-hooks/*.sh`，放脚本即跑

### 5.2 大核 offline 的真相（省电调度核心）

**最初假设**：thermalloadalgod（MTK 省电调度算法）负责大核 offline，它依赖 system_server。

**二进制逆向证明**：thermalloadalgod **完全不依赖 binder/system_server**（NEEDED 无 libbinder，导入符号 binder 计数=0）。它对接的是"内核 thermal 驱动 + TA(control) socket"。

**最终发现**：**大核 offline 的真相是"TWRP ramdisk 环境不跑框架"**（不是 thermalloadalgod 主动调度）：
- normal idle：大核 offline（0）✅
- boot_slim idle：大核 online（1）❌
- **hybrid（TWRP ramdisk）idle：大核 offline（0）✅** ← 这就是省电的关键

**thermalloadalgod idle 时 ticks 不动**（在等内核 thermal netlink notify），**它不主动调度**。大核 offline 是 TWRP 环境的副作用（不跑框架 → 没人保持大核在线）。

### 5.3 内存省 530M（砍框架的收益）

| 环境 | 内存使用 |
|---|---|
| normal（跑框架） | ~2GB |
| hybrid recovery（不跑框架） | ~447MB |
| **节省** | **~1.5GB** |

**砍掉的**：zygote、system_server、ART、systemui、meizu/flyme UI app。
**保留的**：MTK 守护（fuelgauged/thermalloadalgod/thermald）、chroot 服务（sshd/cpa/freellmapi）。

## 六、最终方案的完整产物清单

### 6.1 镜像

- **`hybrid-hooked.img`**（18776064 B）：normal 内核 + TWRP ramdisk + twrphook 钩子机制，**已刷入 recovery 分区 p1**
- `twrp_slim.img`（18753615 B）：早期尝试，逻辑烧进镜像
- `twrp.img`（18814976 B）：干净原版 TWRP 基座
- `twrp-magisk.img`（19087360 B）：带面具 TWRP（走不通，Magisk 在 recovery 会 abort）

### 6.2 钩子脚本（`/data/local/tmp/twrp-hooks/`）

- `01-fuelgauged.sh`：启动电池守护
- `02-wifi.sh`：wmt+固件+wpa_supplicant+reassociate
- `20-chroot-mount.sh`：挂 Debian chroot
- `30-chroot-services.sh`：起 supervisord
- `40-adbd-tcp.sh`：开无线 adb
- `50-static-ip.sh`：配静态 IP+路由
- `twrp-hook.sh`（在 `/sbin/`）：runner（扫描钩子目录，执行脚本，过滤 Aborted）

### 6.3 配置文件

- `/data/wpa.conf`：WiFi 配置（SSID/PSK）
- `/data/debian/etc/supervisor/supervisord.conf`：supervisord 配置
- `/data/debian/etc/resolv.conf`：DNS

### 6.4 项目目录

- **Z: 盘（项目盘，只读）**：`Z:\my-project\magisk-chroot-boot\`
  - `system/`：Magisk 模块（7 个，system 版，已工作）
  - `twrp/`：TWRP 版模块（4 个，recovery 版，本项目重点）
- **设备**：`/data/debian`（chroot）、`/data/adb/modules/`（Magisk 模块）、`/data/local/tmp/twrp-hooks/`（钩子）

## 七、关键路径与命令（快速查）

### 7.1 刷镜像（只刷 recovery p1，不碰 boot p22）

```bash
# 在安卓里（推荐）
adb push hybrid-hooked.img /data/local/tmp/
adb shell su -c "dd if=/data/local/tmp/hybrid-hooked.img of=/dev/block/mmcblk0p1; sync"

# 进 TWRP 后
adb push hybrid-hooked.img /sdcard/
adb shell dd if=/sdcard/hybrid-hooked.img of=/dev/block/mmcblk0p1

# fastboot
adb reboot bootloader
fastboot flash recovery hybrid-hooked.img
```

### 7.2 回滚（原版 TWRP 备份）

```bash
dd if=/mnt/shared/新建文件夹/twrp.img of=/dev/block/mmcblk0p1
```

### 7.3 adb 连接

```bash
adb -s 621QECQ83QBVM shell   # USB 直连
adb connect 192.168.31.213:5555   # 无线
```

## 八、一句话总结

**通解 = 原厂内核（驱动 built-in）+ hybrid 合成（normal 内核 + TWRP ramdisk）+ 钩子机制（`/data/local/tmp/twrp-hooks/*.sh`）+ 挂载（/system、/vendor）+ chroot（/data/debian），不碰内核源码、不需要安卓框架、不改 boot 分区。**

**用户"既要又要"的正解 = hybrid recovery**：normal 内核驱动全（"既要"）+ TWRP ramdisk 不跑框架（"又要"）+ 钩子灵活（放脚本即跑，不改镜像）。
