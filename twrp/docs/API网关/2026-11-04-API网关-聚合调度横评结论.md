# API 网关「聚合调度」横评结论

> 2026-11-04 · 横跨 CLIProxyAPI / ccswitch / freellmapi / 9router 等多家网关之后，得出的结论。
> 全部结论基于本次实测（9router 本机源码、`/v1/models` 实际返回、supervisor 配置、cpa 配置），未深测的已标注。

---

## 1. 我到底在找什么

手里一堆 AI 账号（agnes、SenseNova、pie-xian、iamhc、hybgzs、elysiver 等 10 来个 key），来自多家上游，质量参差不齐、会挂会限流。

我想要一个**聚合网关**：

1. **一个入口**（一个端口、一个 key）
2. **一个 `auto` 模型** —— 请求它，网关**自动**从整个账号/模型池里挑一个能用的、最合适的，自动做负载均衡 + 故障转移 + 自适应选模型
3. 不要再让我手动指定 `provider/model` 这种前缀式模型名

结果试了一圈，**没有一家满足第 2 条**。

---

## 2. 横评：各网关本质

| 网关 | 端口 | 本质 | 模型暴露方式 | 调度能力 | 聚合 `auto` |
|---|---|---|---|---|---|
| **CLIProxyAPI (cpa)** | 8317 | 模型池 + 按模型名转发 | 各 provider 模型并集，带前缀 | 同账号池按模型名轮询 | ❌ 无（上游自带的除外） |
| **ccswitch** | — | 模型池 + 转发 | 未深测 | 未深测 | ❌ |
| **freellmapi** | 3001 | 模型池 + OpenAI 兼容转发 | 按 key 的模型并集 | 基本无 | ❌ |
| **9router** | 20128 | 模型池 + 按模型名转发 + 显式调度 | 各 provider 模型并集，带前缀 | 同模型多账号 fallback/轮询/配额、Combo、System One | ⚠️ 需手动配 Combo 才有 |

**核心结论：这四家在"模型暴露"上是同一个路数 —— 都是把各 provider 的模型拉出来并集，加上前缀（`iamhc/xxx`、`agnes/xxx`）转发。没有任何一家"凭空"聚合成一个全局 auto 模型给你。**

---

## 3. 关键实测发现（9router v0.5.112）

拿它实测 `/v1/models`，返回 25 个模型：

```
iamhc/auto                 ← 注意这个
mmf/mimo-auto              ← 和这个
agnes/agnes-3.0-flash      SenseNova/deepseek-v4-flash   iamhc/DeepSeek-V4-Flash   ...
```

**这里就有"auto"，但它是假的（对我们没意义）：**

- `iamhc/auto` 是 **iamhc 服务端自己暴露的 auto**，`mmf/mimo-auto` 是 **mmf 自己暴露的**。9router 只是把它们当一个普通模型**透传**，调度逻辑在上游手里，是个黑盒。
- 9router 自己**没有**聚合出一个 auto。

cpa 同理：`/opt/CPA/config.yaml` 里同样透传了上游的 `name: "auto"`，且 `force-model-prefix: false` —— 一样的路数。

---

## 4. 那 9router 的"调度"到底在哪儿

它其实有调度能力，只是**不体现在"auto 模型名"上**，而是要显式用：

| 机制 | 是什么 | 怎么触发 |
|---|---|---|
| **同模型多账号池** | 请求 `agnes/agnes-3.0-flash` → 在 3 个 agnes key 间自动 round-robin / fallback / 配额 | 连接页自动生效（最接近"账号池调度"） |
| **Combo** | 把多个模型绑到一个名字，请求它 → 按策略自动选（smart 用 judge model 评估选最优）或 fusion 融合 | `/dashboard/combos` 手动配 |
| **System One** | 请求分类后用 router model 自动决定用哪个模型 | 设置里配 |

**想要"真·auto 聚合调度"，9router 能做，但得手动配一个 Combo（可以叫 `auto`），加进你想用的模型，策略选 `smart`。** 这样请求 `auto` 才会真正自适应选路 —— 而不是靠一个开箱即用的 auto。

---

## 5. 结论：为什么"一路货色"

因为**"模型池 + 按模型名转发"是这个品类的地板**，所有网关都长在这个地板上，差别只在调度层往上叠多少：

- **地板层（全都有）**：模型并集 + 前缀转发。→ cpa、ccswitch、freellmapi、9router 全一样。
- **调度层（谁叠得多）**：
  - 9router：同模型多账号 fallback + combo(smart/fusion) + systemone + 配额/RTK —— **最全**
  - cpa：账号池按模型名轮询 —— 中等
  - freellmapi：基本纯转发 —— 弱
  - ccswitch：未深测

**所以"开箱即用的 auto"不存在，只有两条现实路径：**

1. **吃上游自带的 auto**（`iamhc/auto`、`mmf/mimo-auto`）—— 省事，但调度是上游黑盒，你管不了、模型也不一定全。
2. **用 9router 的 Combo+smart 显式配一个 auto** —— 自己能控、真自适应，但要自己配模型列表。

---

## 6. 我的推荐

**如果核心诉求是"一个 auto + 全池自适应调度"：**

> 留在 9router，去 `/dashboard/combos` 配一个 `auto` Combo，把你那 20+ 个能用的模型加进去，策略选 **smart**（judge model 自动评估）。之后直接 curl `auto`，它会自己挑。这是目前唯一能让你"一个入口 + 自适应"的路。

**如果不执着于 auto，只想稳定用：**

> 9router 单层就够：模型并集 + 同模型多账号自动 fallback（账号池调度已内置），不用再套 cpa。**别把 cpa 放 9router 前面** —— 两层都是"模型池"，前面的池子会闲置，还白添一层损耗。

---

## 7. 9router 的坑（用之前知道）

1. **禁用模型不可靠**：自定义 provider 的禁用模型可能"复活"（GitHub #2768、#3115），得定期复查 `/v1/models`。
2. **UI 缺 Custom Headers 入口**：自定义 provider 页面默认不显示 Custom Headers 区，得先用 API `PUT /api/providers/[id]/overrides` 种一个 header，UI 才出现可编辑区。
3. **`/api/provider-nodes` 无鉴权**：别把这个端口暴露公网，否则任何人能改你的节点。
4. **两层架构浪费**：cpa 在前 + 9router 在后 = 重复做账号池，cpa 池闲置。
