# chroot /system 启动 SurfaceFlinger：可行性预演与资源占用

**日期**：2026-11-04
**设备**：魅蓝 Note5（MT6755，Mali-T860 MP2，Android 7.0 Flyme 7.0.1.0A，kernel 3.18.35，4 核，3GB RAM）
**状态**：chroot /system 地基**已验证成立**；真正启动 SF 需等 TWRP 环境（当前完整 Android 的 SF 已占用）

---

## 一、方案本质（双 chroot 容器，不缝合）

```
TWRP recovery（宿主机）
 ├── chroot /system        → Android 原生环境（跑 surfaceflinger/servicemanager/hwcomposer）
 │     └── 全原生 bionic：linker64 + /system/lib64 + /system/vendor/lib64
 └── chroot /data/debian   → Debian 环境（跑 X11/桌面 + libhybris）
       └── libhybris → 连到 /system 的 SF/hwcomposer（经共享 /dev/mali0 + binder）
```

**关键**：两个 chroot **各是各的，不缝合**。`/system` chroot 跑 Android 显示栈（原生 bionic），`/data/debian` chroot 跑 Linux 桌面。通过**共享 GPU/显示设备节点**（/dev/mali0、/dev/graphics/fb0、/dev/binder）和 binder 关联。

---

## 二、预演结果（2026-11-04 实测，当前完整 Android 上测 chroot 可行性）

### 预演1：surfaceflinger 库依赖解析 ✅ 13/13 全 OK

`libbinder` `libgui_ext` `libsurfaceflinger` `libgralloc_extra` `libgui` `libhardware` `libEGL` `libGLESv2` `libion` `libion_mtk` `libui` `libutils` `libcutils` ——全在 /system 可解析。

### 预演2：servicemanager 依赖 + binder 通路 ✅
- servicemanager 依赖（libbinder/libutils/libcutils/liblog/libc++.so）全 OK
- `/dev/binder` 存在（10,49，`crw-rw-rw-` 666，任何用户可访问）

### 预演3：chroot /system 直接建（mkdir + bind）❌
- `/system` 分区 **ro 只读**，`mount -o remount,rw /system` **失败**（`Device or resource busy`）
- 无法在 /system 内 mkdir /dev /proc /sys 挂载点
- **结论**：不能直接把只读 /system 当 chroot 根

### 预演4-7：改用可写 chroot 根 + bind /system ✅（最终方案）
```
mkdir -p /data/chroot-system/{dev,proc,sys,tmp,system,vendor}
mount --bind /system /data/chroot-system/system     # /system 分区 bind 进 chroot 根
mount --bind /dev   /data/chroot-system/dev          # 设备节点（binder/mali0/fb0）进去
mount --bind /proc  /data/chroot-system/proc
mount --bind /sys   /data/chroot-system/sys
```

**关键发现**（预演7 成功）：
```bash
# LD_LIBRARY_PATH 必须含 vendor lib64，否则 linker64 找不到 libdirect-coredump.so
export LD_LIBRARY_PATH=/system/lib64:/vendor/lib64:/system/vendor/lib64
chroot /data/chroot-system /system/bin/sh -c "echo ENTER_OK"
# → ENTER_OK（成功进入 chroot /system）
# → 能列出 /system/bin/surfaceflinger /system/bin/servicemanager
```

**结论**：chroot /system **可操作性 100% 验证**。`/system` 不能直接当根（ro），但 **bind 进可写 /data 下的 chroot 根即可**，效果等同（/vendor symlink → /system/vendor 天然在内）。

| 项 | 占比 |
|----|------|

## 五、启动 SF 会容易吗（你问的核心）

**✅ 容易**，因为 chroot /system 后：
1. 全原生 bionic 环境（linker64 + /system/lib64 + /vendor/lib64），**不借不桥不缝**
2. 库依赖 13/13 解析（预演1）
3. binder 通路在（/dev/binder 666）
4. 设备节点权限已正确
5. servicemanager/surfaceflinger 二进制在 /system/bin
6. /vendor symlink → /system/vendor 天然在内

**✅ 和正常 Android 启动环境一致**：正常 Android 里 SF 能初始化 hwcomposer（`dumpsys SurfaceFlinger` 验证活着：`[sf] [libui] [libgui]` + EGL sync + DispSync 60Hz），说明**这套栈在设备上本来就工作**。chroot /system 是**原样复现**，环境一致。

**⚠️ 唯一未知**：MTK hwcomposer 的 overlay session（`no session 196610 found`，闭源 vendor 逻辑）——SF 内部初始化它。**必须等 TWRP**（当前 Android 的 SF 已占用，不能起第二个）。

**成功率估计**：**60-70%**（环境原生匹配；唯一风险是 SF 可能隐式依赖 zygote/system_server 的 binder 服务）。

## 六、启动步骤（等 TWRP 时执行）

```bash
# 1. 建 chroot 根 + bind（/data/chroot-system，或直接 /data/debian 复用）
mkdir -p /data/chroot-system/{dev,proc,sys,tmp,system,vendor}
mount --bind /system /data/chroot-system/system
mount --bind /dev   /data/chroot-system/dev
mount --bind /proc  /data/chroot-system/proc
mount --bind /sys   /data/chroot-system/sys
export LD_LIBRARY_PATH=/system/lib64:/vendor/lib64:/system/vendor/lib64

# 2. 起 servicemanager（binder 服务注册）
chroot /data/chroot-system /system/bin/servicemanager &

# 3. 起 surfaceflinger（初始化 hwcomposer + display session）
chroot /data/chroot-system /system/bin/surfaceflinger &

# 4. 验证：logcat 看 createOverlaySession / 无 "no session"
# 5. chroot /data/debian 里 libhybris 连过去（EGL_PLATFORM=hwcomposer）
```

---

## 七、成败判定（1 小时内出结果）

- **通**：SF 起来 + hwcomposer 建 session（无 `no session`）→ **零拷贝打通**
- **不通**：SF 仍报 `no session` 或崩 → MTK 闭源 vendor 逻辑限制，此路确实不通

## 八、残留说明

预演用的 bind 挂载在 `/data/chroot-system`（用户数据分区），**不影响 /system、不影响 Android 正常运行**，重启后自动消失。预演未改动 /system 分区本身。
